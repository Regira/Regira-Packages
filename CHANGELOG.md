# Changelog

Release summary for the Regira NuGet packages — newest first. Every change that ships in a package
adds one bullet under **Unreleased** in the same change (format: `` `PackageId` x.y.z — summary ``),
and leaves that package's `<Version>` higher than its last published version. At publish time the
Unreleased block becomes a dated release heading.

## Unreleased

- `Regira.Office.Clients` 6.2.0 — new `ILicenseStatusClient` (`GetStatus()`), registered by `AddOfficeClients`, calling the hosted API's `GET /license/status` with the same `X-License-Key` the other clients send. Returns the `LicenseStatus` from `Regira.Licensing` for any key, an expired one included, so an application can log why its Office calls are suddenly rate-limited and when its key must be renewed.
- `Regira.Office` 6.2.0 — guide-only: `office.namespaces` lists `LicenseStatusClient` / `ILicenseStatusClient`.
- `Regira.Licensing` 6.2.0 — **behaviour change:** `LicenseValidator.Validate` keeps accepting a key for a short period after its expiry date instead of refusing it on the day itself, so an owner who missed the renewal date has time to act. The length of that period is deliberately unspecified and not configurable; it is a courtesy, not part of the license terms, and may change between versions. `UseRegira` writes a renewal reminder to the console when a registered key expires within `LicenseValidator.RenewalReminderPeriod` (two weeks), and a warning to the console's error stream once the date has passed, so an owner sees the prompt at startup rather than in the first request a licensed module refuses. New `LicenseValidator.GetStatus(key, productCode)` returns a `LicenseStatus` (`LicenseState` missing / invalid / not accepted / expired / expiring soon / valid, customer, expiry, days left, the key's own limits, one-line message, and an `Applied` line that only the answering host fills in) without throwing — the shape the hosted APIs and the MCP server serve so a consumer can ask about a key that no longer works. `licensing.md` now states what actually happens to an expired key (it is refused) instead of claiming a fall-back to the free tier, and points at the status tool and endpoint.
- `Regira.Web` 6.1.4 — guide-only: the Web family tables and installation snippets (packed `web.instructions` and the package README) name the new `Regira.Web.Analytics` and `Regira.Web.Analytics.GeoIP2` packages.
- `Regira.Web.Analytics.GeoIP2` 6.2.0 — new package: the geolocation provider for `Regira.Web.Analytics`, and the only package in the family carrying the `MaxMind.GeoIP2` dependency. `AddGeoIP2(configuration)` on the analytics builder registers an `IPageViewEnricher` that resolves country and city from a **local** GeoIP2/GeoLite2 `.mmdb` (`Analytics:GeoIP2:DatabasePath` — a file or a directory, City preferred over Country; missing → disabled with a log line, never a throw) on the unmasked client IP before masking, so visitor addresses never leave the server. Any entity implementing the shipped `IGeoPageView` opts in; `GeoPageView` (`PageView` + the three columns) is provided for hosts without an entity of their own. The lookup sits behind `IGeoLocationService`, registered with `TryAdd`, so another provider or a test fake replaces MaxMind without touching the enricher. Loopback, link-local and private ranges are skipped.
- `Regira.Web.Analytics` 6.2.0 — new package: abstract visit tracking for ASP.NET Core. A filterable middleware captures page views into a bounded queue and a background writer batches them to consumer-registered hooks — an `IVisitFilter` (which requests count; the default tracks HTML page loads), in-request `IVisitContributor`s (live-HttpContext data such as request-body details), background `IPageViewEnricher`s (run on the unmasked client IP before it is truncated — the geolocation seam), and an `IPageViewStore` for persistence, which the package deliberately does not ship: no storage, geo or EF dependency, only `Regira.Web`. Client IPs are stored masked to configurable prefix lengths (`Ipv4PrefixLength`/`Ipv6PrefixLength`, /24 and /48 by default); an out-of-range value falls back to the default with a warning, never to the full address. `AnalyticsBuilder.Enabled` exposes the on/off state so extension packages (`Regira.Web.Analytics.GeoIP2`) guard their registrations on it too. The pipeline is generic over the entity — `AddAnalytics<TPageView>` records any `IPageView` implementation (the shipped `PageView` is the default and the convenient base) so host dimensions are typed columns, not a property bag. Optional `X-Analytics-Key`-protected `GET /analytics/stats` maps only when the registered store implements `IPageViewStatsStore`; retention purges only through an `IPageViewRetentionStore`. Bot markers compile into the package (merge/override via `Analytics:BotDetection`, plus an optional watched `botdetector.json`); forwarded-headers handling is left to the host, and the docs state the ordering contract instead.
- `Regira.Entities.EFcore` 6.2.0 — new `SaveChangesBreakingDeleteCycles` / `SaveChangesBreakingDeleteCyclesAsync` (`Regira.Entities.EFcore.Extensions`) for two rows deleted together that reference each other — the shape an entity produces when it carries a foreign key to one of its own children. EF Core refuses the whole save with *a circular dependency was detected in the data to be saved*, so `IEntityService.Remove` + `SaveChanges`, and therefore the generated `DELETE` route, answers 500 for every owner whose children are loaded. Nothing inside `SaveChanges` can resolve it: primers and preppers do run for deleted entries, but EF orders the deletes from the **original** foreign-key values, so what they set is never read — and faking the original value only moves the failure to the database, which still holds the reference while the row it points at is deleted. The extensions are called **from the context's own `SaveChanges`/`SaveChangesAsync` overrides** (both of them) and drop the optional side of the pair in an `UPDATE` before the `DELETE`s, in one transaction and through the context's execution strategy — a transaction the caller already owns, its own or an ambient `TransactionScope`, is joined rather than nested, which is what keeps the shape working under `EnableRetryOnFailure()`: EF's own recipe for combining the two puts the save inside a strategy the caller owns, and a second transaction in there is a second unit of work the retry cannot replay. The strategy itself is not the hazard: nested inside the caller's it is suspended, and a bare `BeginTransaction()` with no strategy around it is refused by EF's own `SaveChanges`, with or without the extension. The ambient case is the one that cannot be inferred — `Database.CurrentTransaction` is null inside a `TransactionScope`, so the extension checks `Transaction.Current` too, where beginning a transaction on the enlisted connection would throw. `acceptAllChangesOnSuccess` goes to the extension and reaches the delegate as a parameter, because which phase may accept is not the caller's to choose: the reference-dropping `UPDATE` is always accepted — EF reads the delete order back from those entries, so leaving them pending re-raises the very circular dependency and re-sends every other change in the save alongside it — while `false` is honoured on the final save, where `SaveChanges(false)` + `AcceptAllChanges()` expects the deletes to still be pending. A save with no such pair calls the real save exactly once and opens no transaction. Direct pairs only: a longer ring (`A → B → C → A`) is left to EF's own exception rather than resolved by guessing which link is incidental.
- `Regira.Entities.DependencyInjection` 6.2.0 — startup validation warns when the model has an entity referencing one of its own children while the child's foreign key cascades back. Neither failure the shape produces names the relationship: SQL Server refuses the migration with a raw `Msg 1785` ("may cause cycles or multiple cascade paths", and only when the reference is not mapped `ClientSetNull` — SQLite never enforces it, so an app that develops on SQLite meets it at the migration), and the delete fails at run time with EF's own circular-dependency text. The warning names both foreign keys, the `ClientSetNull` mapping when the reference would add a second cascade path, and the two ways out. One warning per reference rather than per pair of types — an owner pointing at the same child type twice (a cover and a thumbnail) is two cycles, each with its own answer — while a pair that cascades both ways is still reported once rather than from both ends. A warning rather than an error: the model alone cannot prove the reference ever points at a child of that same owner. The context-type resolution shared with the two archived-filter validators moved into one internal helper.
- `Regira.Entities` 6.2.0 — the packed guides gain *An entity that references one of its own children* (`entities.patterns`), covering both failures, the `ClientSetNull` mapping and the two-phase delete, and leading with the cheaper answer: mark the child (a flag, or a rank column it already has) instead of pointing the owner at it, which removes the foreign key and both failures with it. Both dead ends are written down so they are not rediscovered — a primer nulling the property does nothing, and faking the original value only moves the failure into the database. Cross-referenced from `entities.instructions` (§Attachments and the recipe index), a `how_to` recipe (`primary-child`), `entities.signatures`, and the repository's `docs/models.md`.
- `Regira.TreeList` 6.2.0 — **behaviour change:** `OrderByHierarchy(keySelector)` sorts the roots and the children of every node by the key, level by level, as the README always described. It applied one `OrderBy` to each root's whole flattened offspring instead, so a grandchild could be emitted before its own parent and any indentation driven by `Level` came out corrupted. The parameterless overload is unchanged (pre-order, insertion order within a level). It ships as a minor rather than a major because the old order was never a contract: the README, the packed guide and the method's own XML doc all promised sorted siblings with the parent first, and a caller wanting the flat order can sort the flat list itself.
- `Regira.TreeList` 6.2.0 — **behaviour change:** the parents-selector builds (`Fill(values, getParent)`, `Fill(values, getParents)` and the `ToTreeList` overloads on top of them) now throw `InvalidChildException<T>` when input values remain that no root can reach — they take part in a cycle, or their parent object is missing from the collection — instead of silently leaving them out of the tree. They derive the roots from the values without a parent and then only walk downwards, so a cyclic value (every member of a cycle has a parent) was never visited and `ThrowOnError` never engaged: the throw the README documented did not happen on this path. `ThrowOnError = false` keeps the silent skip, which is the migration path for a caller that was relying - knowingly or not - on the partial tree: a build that used to return quietly now throws at runtime, and that is the one change here a green compile will not warn you about. It ships as a minor because the README documented this throw from the start; the code simply never performed it. A value with several parents still occupies one node per parent, which is not a cycle and is not reported.
- `Regira.TreeList` 6.2.0 — **source-breaking:** `TreeNode<T>.AddChild` returns `TreeNode<T>?`. Under `ThrowOnError = false` — the silent-skip mode the option promises — it threw `InvalidOperationException: Sequence contains no elements` instead of skipping, because it read `.First()` off the empty result of a rejected `AddChildren`. It now returns `null` like `TreeList<T>.AddValue` always did, and the children-selector fill skips the rejected subtree rather than following it. Consumers under `<Nullable>enable</Nullable>` that pass the result on will see a nullable warning at the call site - a warning, not an error, and the compiled assembly is unchanged, which is why this is a minor: the signature now states the null the method could always return.
- `Regira.System.Projects` 6.2.0 — `ProjectTree.Load` null-guards the recursive descent after `TreeNode.AddChild`, which now returns `TreeNode<T>?` (see the `Regira.TreeList` entry above); without it the walker would follow a subtree that was never added, and the package would not compile clean under `<Nullable>enable</Nullable>`. No change to the `ProjectTree` API.
- `Regira.Entities` 6.2.0 — `entities.blueprints`' multi-tenancy gotchas contradicted the mechanics the other guides describe, on the two points a reader would only discover in production. Global filters run for direct `IEntityService` reads **including when no tenant resolves**: the unconditional `Where` compares `TenantId` against `null` and yields an empty view, so a background job without a tenant sees nothing, not everything as the guide said — an agent following it would have skipped setting `WritableTenantContext.TenantId` and shipped a job that silently processed zero rows. And the tenant predicate is key-agnostic (it never reads the search object), so the int variant alone already scopes entities of every key type; the guide demanded a per-key registration that a non-int entity does not need, while the real rule — register `<TKey>` variants for filters that read typed search-object fields — went unsaid. The repository's `docs/normalizing.md` drops the same "converts to lowercase" claim that `entities.instructions`/`entities.signatures` corrected in 6.1.3: `NormalizeOptions.Transform` defaults to `NoChanges`.
- `Regira.Office.Mail.MailGun` 6.2.0 — a failed send throws `MailException` carrying Mailgun's own response body on `ResponseContent`, like the SendGrid backend and the Peppol services already did; it threw a plain `Exception` naming only the status code, so every refusal reached the caller as `Failed. Status: BadRequest` with the provider's explanation discarded. Diagnosed against a live EU outage where the body (`failed to validate domain` on the neighbouring stats route, a bare `Internal server error` on `messages`) was the only thing separating a provider fault from a malformed request. `MailException` derives from `Exception`, so an existing `catch (Exception)` is unaffected; an unauthorized response still throws a plain `Exception`.
- `Regira.Office` 6.2.0 — the mail guides said a `catch (MailException)` block does not catch Mailgun send failures. It does now, and both the packed `office.mail.instructions` and the developer README say so, adding that the provider's reason lives on `ResponseContent` rather than in the status code.
- `Regira.Entities` 6.2.0 — new **`[ServerOwned]`** attribute (`Regira.Entities.Attributes`) plus the preppers that enforce it (`AutoServerOwnedPrepper`, `ServerOwnedPrepper<TEntity, TProp>` in `Regira.Entities.Preppers`). A marked scalar or FK is restored from the stored row on update, so a PUT/PATCH that omits it — the normal consequence of leaving it off `TInputDto` — can no longer null it or overwrite it, the failure that turned a status-only PATCH into a zeroed `Total` and needed a hand-written primer per entity until now. Enforcement is a **prepper**, not a primer: it guards the `IEntityService` write path and leaves a domain/workflow service's raw `DbContext` write alone, which is also why `ArchivablePrimer`'s delete-to-update is not reverted. Scalars and FKs only — a navigation, a property without both accessors and `IArchivable.IsArchived` (a restore has to be able to clear it) are not protected; `ServerOwnedProperties` exposes the resolved sets. Packed guides updated: the *Server-owned / immutable fields on update* recipe now leads with the declaration and keeps the prepper/primer forms for what it cannot cover.
- `Regira.Entities.DependencyInjection` 6.2.0 — `e.ServerOwned(x => x.Code, mintOnCreate?)` on the entity builder and inside a `Related()` block, for the create-time mint an attribute cannot carry; an invalid selector throws at registration rather than at the first write, and every builder variant re-declares it covariantly so it chains into the int-keyed `Related<TRelated>` shortcut. New `AddDefaultPreppers()`, called by `UseDefaults()`, registers the attribute's enforcement for every entity — inert until an entity marks a property, and registered first so an entity's own prepper can still take a marked field over. `Related()` now also runs it on owned children, which are written through the parent's prepper chain rather than their own write service. Startup validation gains a check that fails on a `[ServerOwned]` declaration nothing can enforce and warns when no enforcement is registered at all.

## 6.1.3 — 2026-08-26

- All packages — version aligned at 6.1.3 for a whole-family publish. Ten packages carry a change of their own: `Regira.Entities`, `Regira.Entities.EFcore`, `Regira.Setup` and `Regira.Security.Authentication.Web` below, plus the six dependency moves at the end of this block. `Regira.Web` 6.1.3 is a comment-only clarification in `ControllerExtensions.File` — the 404-before-headers behaviour it describes shipped in 6.1.2 and is unchanged. The remaining packages are republished unchanged so the family shares one version.
- `Regira.Entities.EFcore` 6.1.3 — the attachment file-name filters built their SQL `LIKE` patterns from the **normalized** keyword but compared them against the raw `FileName` column: the default normalizer drops `.` and turns `-` into a space, so `?fileName=my-report*` searched `my report%` and matched nothing. `Extension` was worse — it interpolated the *input* wildcard into the pattern (`*pdf`) instead of SQL's `%`, an exact match on a file literally named `*pdf`. Both now build from the raw keyword minus its wildcards, in `AttachmentFilteredQueryBuilder`, `EntityAttachmentFilteredQueryBuilder` and the `EntityAttachmentQueryExtensions.Filter` extension; exact (wildcard-free) matching is unchanged. `Extension` is now anchored on the separating dot, so `?extension=pdf` matches `report.pdf` but not `handbook-nopdf` — strictly a gain against 6.1.2, where it matched nothing at all. Because the file name reaches the pattern verbatim, a `%` or `_` in a search value keeps its SQL `LIKE` meaning (`?fileName=my_report*` matches `my-report.pdf`): it over-matches, never under-matches, and is not injection — EF parameterizes the pattern. File-name filtering only, not filter parity — `EntityAttachmentFilteredQueryBuilder` still implements `ObjectId` and `FileName` alone.
- `Regira.Entities.EFcore` 6.1.3 — **behaviour change:** `QueryExtensions.FilterQ`'s explicit-fields overload now matches `QKeyword.TrimmedQW` instead of `QW` — the raw keyword, not the normalized one. It serves entities that are *not* `IHasNormalizedContent`, so the columns a caller names hold the client's value verbatim; against the normalized pattern `?q=ORD-2024-001` searched `%ORD 2024 001%` and matched nothing, while plain alphanumeric terms worked — a silent, punctuation-shaped failure. The `ParsedKeywordCollection` overload for `IHasNormalizedContent` is unchanged. A caller who pointed this overload at a *normalized* column must now build that predicate with `QW` itself; the XML doc and `entities.instructions` say so where they used to advise preferring normalized columns.
- `Regira.Entities` 6.1.3 — `QKeyword` gains a **raw** keyword family: `TrimmedStartsWith`, `TrimmedEndsWith`, `TrimmedQ` and `TrimmedQW`, completing the raw side against the existing `Trimmed`. They hold the same patterns as `StartsWith`/`EndsWith`/`Q`/`QW` but built from the trimmed input rather than the normalized one, for `LIKE`s against a column that stores the client's value verbatim (a file name, a reference code). The existing members are unchanged: everything without the `Trimmed` prefix is normalized, as `Q`/`QW` always were. Matching a family to the wrong column compiles and silently matches nothing, so `QKeyword` now documents the split on the type itself.
- `Regira.Entities` 6.1.3 — the *Match the keyword family to the column* callouts in `entities.instructions` and `entities.signatures` claimed the default normalizer **upper-cases**, offering `my-report.pdf` → `MY REPORTPDF` as the worked example. It does not: `NormalizeOptions.Transform` defaults to `NoChanges` and the registered `DefaultNormalizer` is built from it, so case is preserved and the real lookup value is `my reportpdf` — as the same file's normalize-contract table said 58 lines earlier. An agent reading the old text would write `.ToUpper()` into a normalized-column comparison and reintroduce the exact silent no-match the callout exists to prevent. Both callouts now also carry the `%`/`_` consequence of the raw `Trimmed*` family that the `Regira.Entities.EFcore` entry above spells out, so it is stated where a consumer wiring `TrimmedQW` into their own filter will meet it.
- `Regira.Entities` 6.1.3 — `entities.setup` names the `Microsoft.AspNetCore.OpenApi` floor `Regira.Security.Authentication.Web` sets (`10.0.11`) and the `dotnet new webapi` pin below it (`10.0.10`), and adds that package before the `Regira.*` ones so adding sign-in later cannot downgrade it. Also corrects the severities: NU1603 warns, **NU1605 is an error** and fails every restore and build until cleared.
- `Regira.Entities` 6.1.3 — the `Supplier` slice in `entities.examples` used `[Route("[controller]")]`, which expands to the class-name stem: `SupplierController` served `/Supplier`, not the kebab-case plural `/suppliers` the paired SPA calls, so the one example marked copy-paste-safe 404'd every list request for that entity. It now spells the resource like the file's other controllers, and the guidance in `entities.instructions` → *Web endpoints* and `entities.setup` → *API route prefix* drops the token. `entities.setup` also shows `UseCentralRoutePrefix`'s call site (`AddControllers(o => …)`, since it extends `MvcOptions`).
- `Regira.Setup` 6.1.3 — `project.setup`'s *Key auth model types* listed the types under the **package** name `Regira.Security.Authentication`, a prefix of but not equal to any real namespace, so following it produced CS0234; the five namespaces now ship as copyable `using` lines pointing at `security.instructions` → *Namespace Quick Reference*. The NU1605 note gains the `dotnet new webapi` interaction and its recovery.
- `Regira.Security.Authentication.Web` 6.1.3 — the card's version-floor bullet adds the `Microsoft.AspNetCore.OpenApi` **10.0.11** floor beside the existing `Microsoft.OpenApi` one, since the template pin below it is what breaks the first authenticated build.
