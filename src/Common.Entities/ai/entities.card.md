# Regira.Entities — index card (back-end)

> The must-know bullets before scaffolding a Regira Entities API. Drill into `entities.setup`, `entities.instructions`, `entities.examples`, `entities.namespaces`, and `entities.signatures` for detail. **Read economically:** this card + a heading-scoped `get_package` (its `section` + `heading` params; find headings with `get_section_toc`) usually suffices — pull a whole section only when a heading isn't enough. The **project template / host setup** (Program.cs, DI, logging) lives in a separate package — `get_package(id: "Regira.Setup", section: "project.setup")`.
>
> **⚠️ marks failures the toolchain will not catch for you** — silent data loss, or a green build that breaks at startup or on a later request. Anything the compiler names is written plainly.
>
> **⚠️ This card is enough to build with, which is exactly its trap.** Two sections are *not* summarised below and are cheaper to read than to re-derive. Their headings are listed here so you can fetch **one** by name (`get_package(id: "Regira.Entities", section: …, heading: …)`) instead of gambling on the whole file:
>
> `"patterns"` (~70k chars) — the recipes for what goes silently wrong:
> Bulk insert / update · Soft Delete (incl. *Before you make reference data `IArchivable`*, *Attachments on an archivable owner*) · Single-field PATCH / state toggle · Cross-entity aggregates & report endpoints (incl. *Domain actions on an entity resource*) · Owned children that are both sortable and individually togglable · Renamed DTO property · Writing to a related entity from a prepper · Server-owned / immutable fields on update (incl. *Aggregates over a non-owned child collection*, *Server-generated sequential codes*) · Public (anonymous) attachment downloads · An entity that references one of its own children · Audit Trail with Custom Primer · Hierarchical Data · Auto truncate · DbContext Interceptors
>
> `"blueprints"` (~66k chars) — complete proven slices, each one a model you should not rebuild:
> Contact data & addresses (phone/email rows + address lists on any entity) · Stakeholders (parties/people/organizations — also the fix for a busted entity budget) · EntityLabels (free-form tags) · Multi-tenancy · Recursive entities (subtree filters) · Identity users as framework entities · Virtual entity (reference data with no table)

- **Two references for a Web API:** `Regira.Entities.Web` (EntityControllerBase + HTTP endpoints) plus a mapper (`Regira.Entities.Mapping.Mapster`, the default). Everything else in the stack is pulled in transitively.
- **Register with `UseEntities<TContext>(options => …)` then chain `.For<TEntity, …>()` per entity.** `UseEntities` returns the concrete `EntityServiceCollection<TContext>`; write your `Add{Entities}()` extension methods taking `this IEntityServiceCollection<TContext>` and returning the concrete type so chains stay composable.
- **Classify each entity simple or complex first.** *Simple* = any `For<>()` without typed `TSortBy`/`TIncludes`. *Complex* = the overloads with `TSortBy` + `TIncludes` — required for typed sorting/includes and the batch `POST /list` & `POST /search` (`GET /search` exists for simple too). The split also drives the free-tier budget.
- **One writer per save path.** An owned child (order lines, join rows) is synced by the parent's `e.Related()` — no own `.For<>()`, no controller, no budget slot. Adding a `.For<>()` anyway (for a dedicated PATCH route) is supported, on one condition: **the parent's input DTO must leave the collection `null`**, which makes the sync a no-op. If the parent sends it, the parent wins and silently overwrites the child's writes — and `[]` deletes every row while `null` touches none. Decide per entity before scaffolding; reversing it later is the most expensive rework.
- **⚠️ Every scalar/FK field you leave off `TInputDto` is written back as `null`/default on PUT *and* PATCH.** Server-owned values (owner FKs, generated codes, computed totals) silently reset — a status-only PATCH zeroes a computed `Total`, returns 200, and nothing errors. Mark each excluded field `[ServerOwned]` — the write path then restores it from the stored row on update (`e.ServerOwned(x => x.Code, mint)` also mints it on create). Verify with a PATCH round-trip, not just create/read.
- **Constraint violations return 409.** `SaveChanges()` maps a DB integrity-constraint failure (FK, unique index, NOT NULL) to `EntityConstraintException` → 409 Conflict on every write surface, with a generic detail (the provider message is logged server-side). Transient faults (deadlock, timeout) still 500. `EntityInputException` from a prepper → field-level 400.
- **Free-tier budget is two independent buckets:** 5 simple + 2 complex registrations (not a shared pool of 7, and **7 is the hard ceiling**), one slot per distinct entity type; exceeding either throws at startup. Attachments cost one extra simple slot per owner (the per-owner join entity); the shared `Attachment` base registered by `WithAttachments` is free infrastructure, however many owners use it. Classify every entity and tally the budget **before** scaffolding — decision table, overflow remedies and a worked example in `entities.instructions` §Step 0. Over budget? Re-classifying only moves slots; the move that *creates* them is collapsing `Customer`/`Supplier`/`Employee` into one role-discriminated party (blueprint: **Stakeholders**). Register paid keys via `UseRegira(configuration)` once, before `UseEntities()`.
- **⚠️ `DELETE` stops deleting on an `IArchivable` entity** — it flags `IsArchived = true`, same 200, same affected count, and the row then disappears from lists, from included collections, and from `GET /{id}` (404). The archived query filter that hides them is wired into the context's options by `UseEntities<TContext>(e => e.UseDefaults())` — no `DbContext` change; a hand-constructed context takes `.AddArchivedQueryFilter()` on its own options builder, and startup validation errors out naming the entity when a model ends up without the filter. Reads opt back in per request with `?archived=included` (both) or `?archived=only` (the recycle bin). Restore only works while `IsArchived` stays on `TInputDto`, so do **not** exclude it as "auto-generated". ⚠️ **Do not make reference data `IArchivable`.** On `net10.0` the filter propagates into `Include()`, and where the navigation is **required** EF composes it as an inner join: archiving one lookup row silently drops every row referencing it from `items` while `/search` still **counts** them, so pages come back short and nothing errors. Soft delete belongs on aggregate parents (`Order`, whose lines go with it); a category/status/type behind a required FK should be a real `DELETE` with `OnDelete(Restrict)` → 409, or an optional FK. Startup validation warns on the hazardous shape. Only for a genuine aggregate parent is the resulting `PossibleIncorrectRequiredNavigationWithQueryFilterInteractionWarning` expected noise — suppress it via `ConfigureWarnings` on the `AddDbContext` options, and mirror the filter on any dependent you query directly. Full route contract in `entities.patterns` → Soft Delete.
- **Controller generics must mirror the `.For<>()` generics exactly.** `.For<>()` takes N type args; the matching `EntityControllerBase<…, TDto, TInputDto>` takes N+2 (it appends `TDto` + `TInputDto`). A wrong count compiles but fails at startup: in Development the entity startup validation names the exact mismatch and the registered alternatives (enable it in Production via `o.ConfigureValidation(v => v.Enabled = true)`). Don't declare a constructor on the controller — the base resolves its service internally.
- **Required JSON options** via `services.ConfigureDefaultJsonOptions()` (`Regira.Entities.Web.DependencyInjection`): sets `ReferenceHandler.IgnoreCycles` (entity graphs are cyclic), a `JsonStringEnumConverter` for enum sort/includes flags, and `DefaultIgnoreCondition = WhenWritingNull` — on both MVC `JsonOptions` *and* `Http.Json.JsonOptions`. `AddJsonOptions(...)` alone misses the latter, breaking OpenAPI/minimal-API schemas.
- **DbContext plumbing is auto-wired by `UseDefaults()`.** `UseEntities<TContext>(e => e.UseDefaults())` contributes the primer/normalizer/auto-truncate interceptors, the UTC date convention and the archived query filter to the context's options itself — `AddDbContext<T>(options => options.UseSqlite(...))` only needs the provider, and the `DbContext` itself needs no Regira call. The wiring matches by assignability, so registering an **abstract base** context (`UseEntities<AppContextBase>()`) also wires the concrete provider-specific contexts (`AddDbContext<SqlServerAppContext>()`), in any registration order. Without `UseDefaults()`, select pieces via `e.WireDbContext(DbContextWiring …)` flags; in Development the startup validation fails fast when primers exist but no interceptor is wired.
- **`SaveChanges()` is explicit.** Base controllers call it automatically, but when you use `IEntityService` directly (seeding, jobs, custom services) you must `await service.SaveChanges()` yourself. The change tracker is cleared after every save — re-attach via `Modify`/`Save` before mutating again.
- **Includes load on demand, Details loads eagerly.** `Details(id)` always applies all registered includes. On **complex** entities List/Search load only what the client sends via `?includes=` (a `regira` SPA sets it once in `baseQueryParams`); **simple** entities bind no `?includes=`, so a flag-gated include is Details-only — a relation needed on list rows must be eager-loaded **unconditionally** (`e.Includes((q, _) => q.Include(...))`, one cheap reference). An empty nested collection is a missing or wrongly-gated `e.Includes(...)`, not a mapping problem — never `Filter(...)`. **One `Includes(...)` call per entity — a second registration replaces the first**; compose every eager-load in one lambda.
- **Paging counts come from `/search`, not List.** `GET /` (List) returns `{ items }` only; `GET /search` returns `{ items, count }` and exists on every base, simple or complex — point any pager (the SPA overview does) at `/search`.
- **Sorting: use `query.OrderOrThenBy(...)` / `OrderOrThenByDescending(...)`** (`Regira.Entities.EFcore.Extensions`) in `SortBy` builders — they start or continue the ordering. A hand-rolled `is IOrderedQueryable<T>` guard compiles and passes DI validation but throws on the first sorted request.
- **Seeding:** loop `service.Add(item)` to track a batch then one `SaveChanges()`; database-assigned `IEntityWithSerial` `Id`s are populated only during `SaveChanges()`, so save a parent wave before assigning its `Id` to children. Use `Database.EnsureCreated()` for the default disposable SQLite setup.
- **Pin the EF Core provider major to your TFM:** `net8.0`/`net9.0` → `9.x`, `net10.0` → `10.x`. A mismatch builds cleanly but throws `MissingMethodException` on the first query.
- **Blueprints cover these seven; do not rebuild them** — `get_package(id: "Regira.Entities", section: "blueprints")`: **Contact data & addresses** (phone/email rows and address lists on any entity — no party model required), **Stakeholders** (parties + contact data + addresses + typed party-to-party relations — also the fix for a busted entity budget; includes the lighter flat-`Contact` alternative), **EntityLabels** (free-form tags on any entity), **Multi-tenancy** (`IHasTenantId` filter + primer), **Recursive entities** (subtree filters + `Regira.TreeList`), **Identity users as entities**, **Virtual entity** (reference data with no table).
