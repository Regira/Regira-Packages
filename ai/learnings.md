## Lessons Learned

- **The `ai/*.md` guides ARE the MCP's source of truth — keep them in lockstep with the public API.** The knowledge builder copies each package's `ai/` folder into the MCP server's `knowledge/<packageId>/<key>.md` **near-verbatim** — it rewrites relative `.md` links and drops `<!-- no-compile -->` markers, and edits nothing else — so a stale guide makes the MCP confidently return non-compiling code. The generated output is rebuilt from these `ai/` sources — edit the sources, never the generated output. When you add or rename a public API, especially a DI builder extension, update `*.examples.md`, `*.instructions.md`, `*.namespaces.md`, `*.signatures.md` and the `docs/` mirror in the same change. *(2026-06-19)*
- **The source map is syntax-only, so inheritance-only interfaces have empty member lists — the guide is the only contract an agent sees for those types.** The Roslyn scanner walks declared members and never flattens base interfaces; 55 of 278 indexed interfaces currently have zero members but a non-empty `Inherits`. Related kind-sensitivity to preserve when touching the scanner: interface members are *implicitly* public (an explicit `public` must not be required, or every interface indexes empty), positional record parameters are synthesized as members, and enums intentionally keep empty member lists. *(2026-06-19)*
- **Packages without a hand-written signatures file still get an API section, but not a narrative.** The builder synthesizes `api.generated` for any package that has a source map and no signatures guide, so every package now carries at least one section. That is a reflected type surface, not prose — a provider package with no `ai/` folder still teaches an agent nothing about intent, and `ai/` folders are no longer hub-only (several non-hub modules own one). *(2026-06-17)*
- **License slots count distinct entity *types* per tier, not registration calls.** The validator deduplicates each tier and skips the shared attachment base (any type implementing `IAttachment`), so adding attachments to an entity costs exactly one simple slot — the per-owner join registered by `HasAttachments`; the shared `Attachment` base registered by `WithAttachments` is free infrastructure. Any guide quoting attachment slot cost must say "join = 1, base free". *(2026-06-20)*
- **`GET /search` (single, counted) is on *every* controller base — keep the three endpoint tables in lockstep.** Every simple base chains to `EntityControllerBase<TEntity,TKey,TSearchObject,TDto,TInputDto>`, which declares `[HttpGet("search")]`; only the batch `POST /list` and `POST /search` are complex-only. One fact, three docs to sync: the web namespaces guide, the back-end instructions guide, and the front-end instructions guide. *(2026-07-01)*
- **Paging: `PagingInfo.PageSize` is nullable, so the HTTP boundary distinguishes an omitted page size from an explicit `0`.** Omitted (`null`) → `DefaultPageSize`; `pageSize <= 0` (opt-out) → `MaxPageSize`; positive → clamped; `MaxPageSize` is always the ceiling. `UseDefaults()` sets `DefaultPageSize = 10`, `MaxPageSize = 100`. The rule now lives in one shared helper applied at the HTTP boundary (the `Entities.Web` MVC controllers — the only HTTP surface in this repo). The DAL query still applies the value as-is (null or `<= 0` → everything), so a direct `IEntityService` call deliberately bypasses both knobs. *(2026-07-01)*
- **Keep consumer instructions Regira-scoped — the agent is already a .NET/Vue expert, and the bootstrap says so.** General NuGet/EF/Vite/CVE knowledge (vulnerability scanning, EF Core namespace imports, build-tool setup) belongs to the agent, not the guides; the bootstrap's "You are the .NET expert" section names the few cross-cutting traps and stops there. Only genuinely Regira-scoped gaps earn a note — e.g. an advisory that a Regira *default* drags in, or a peer dependency missing from a Regira scaffold. *(2026-07-01)*
- **The authentication web base controllers are "guarded by default", and their docs live in the security hub.** The `*ControllerBase<TUser>` types (account/password/user) carry no per-action `[Authorize]` **by design** — the host is expected to apply a global requirement (`MapControllers().RequireAuthorization(…)`), so every endpoint needs auth and only the five `[AllowAnonymous]` actions are public (`POST auth`, `POST auth/refresh-token`, `auth/password/recover`, `auth/password/reset`, `users/confirm-email`). Do **not** add class-level `[Authorize]`; authorization is a host concern. Concrete subclasses must **not** re-declare `[ApiController]`/`[Route]` — the bases declare them and they are inherited. The package carries only a pointer card; the wiring recipe and endpoint tables live in the hub guide. *(2026-07-02)*
- **Token round-trips must be symmetric, and externally supplied tokens are untrusted input.** Two hard-won rules from the auth endpoints: decode/deserialize of a user-supplied token belongs in a `try/catch` returning **400**, never an unguarded 500 path; and a token must be deserialized as the *same* model it was serialized from — a mismatched model is a case-sensitivity trap that a lenient serializer masks and `System.Text.Json` exposes. Serializing and deserializing directly with `System.Text.Json` avoids requiring an `ISerializer` registration at all. Also: a successful authentication must reset the access-failed count, or the lockout counter never clears. *(2026-07-02)*
- **The JWT default is HS512 and needs a ≥ 64-byte secret — now enforced at registration, because the runtime failure was unreadable.** Before enforcement the symptom was `IDX10720` thrown from the *first login*, i.e. an HTTP 500 on an endpoint that looks like it has a code bug, long after the deploy that caused it and only on the one path that mints a token. `AddJwtAuthentication` now throws `InvalidOperationException` naming the byte count it got and the one the algorithm needs. Two things that shaped the rule: it must be **algorithm-aware** (32/48/64 for HS256/384/512 — an explicit HS256 with a 32-byte key is valid and must keep working), and it needs an **opt-out** (`ValidateSecretLength`), because a scheme that only validates externally-signed tokens needs whatever length the *issuer* used, which `Algorithm` does not describe. Count bytes in `Encoding.ASCII` — that is the encoding the key is derived from, so a secret padded with non-ASCII characters is not as long as it looks. Naming trap: the code constant is `SecurityAlgorithms.HmacSha512Signature` (an XML-dsig URI), while the emitted JWT header and the value to pass when configuring `Algorithm` explicitly are both `"HS512"` — so the rule must recognise both spellings and report the JWA id. *(2026-07-02, enforcement added 2026-07-30)*
- **`Encoding.ASCII` on the JWT secret is load-bearing and must not be "fixed" to UTF-8.** Both `AddJwtAuthentication` and `JwtTokenHelper` derive the signing key with `Encoding.ASCII.GetBytes(secret)`, which folds every non-ASCII character to `?` (0x3F) — so two secrets differing only outside ASCII produce the same key. Widening to UTF-8 derives a *different* key from the same configured secret, which invalidates every token already issued and signs out every session on deploy. It is pinned by a characterization test in `Web.Security.Testing`; if the encoding is ever widened it has to be opt-in per scheme, not a silent correction. Same reasoning applies to `ClockSkew = TimeSpan.Zero` and `ValidateLifetime = LifeSpan > 0`: both are deliberate, both diverge from framework defaults, and both are now pinned. *(2026-07-30)*
- **When one test assembly hosts several independent startups, register controllers through an explicit allow-list.** Multiple startups otherwise contribute every discovered controller to each other, and any shared route template (the auth base's route in particular) collides. A `ControllerFeatureProvider` that replaces the default providers and admits only the intended controllers per startup is the fix. *(2026-07-02)*
- **`_deleted` on an owned/m2m child row is a *mark*, not a delete — the front-end item prep strips only top-level `_`-keys.** The list-item input composable toggles `_deleted` and keeps the row visible, but the base entity service's `prepareItem` deletes only root `_`-prefixed props and does **not** recurse, so a marked child row is still sent and the related-collection prepper keeps it. The delete needs the row **absent** from the payload — filter `_deleted` rows per-collection in a `prepareItem` override. This remains true today; the docs describing it (transient client-only fields, owned collections, m2m selector, item hydration) were corrected to say so. *(2026-07-09)*
- **Verify a reported bug against current source *and* `dist` before acting — a meaningful share of evaluation findings are already fixed or were never real.** Several reported issues turned out to be stale reports against older builds, and nearly every other ask was already covered in the guides. Confirm reproduction against the shipped artifact first; the cost of re-fixing a non-bug is a spurious change to a published package. *(2026-07-09)*
- **A type's own scope set must include the type itself — `GetBaseTypes` returns only what a type derives from.** A global filter scoped to a *concrete* entity (`GlobalFilteredQueryBuilderBase<Order>`) matched nothing and never ran, because the entity side of the applicability test was built from `GetBaseTypes(typeof(TEntity))` alone while the filter side already appended its own type. Interface-scoped filters worked, so every existing test passed over the hole. Two durable lessons: **an inclusion test built from a "base types" helper needs the subject added explicitly**, and **a filter that is silently skipped is indistinguishable from one that passes everything** — for anything security-shaped, prove the filter runs (flip its predicate to `Where(_ => false)` and confirm results go empty) rather than testing only that permitted rows are visible. Applicability now lives in one place shared by the runtime and the startup validator, so the validator cannot vouch for a filter the runtime skips. *(2026-07-20)*
- **Pagination that breaks on a character offset makes later pages unnameable, and agents then fetch all of them.** Slicing guides every `maxChars` cut mid-section and mid-code-fence, so a caller could not tell what page 3 held without spending the tokens to fetch it. Breaking on `##` boundaries and labelling each page with its sections lets a caller skip reference-only pages — but the index must be **bounded and de-duplicated**: labelling every chunk of one oversized section with the parent title emitted 14 identical rows and cost ~32% of a small budget. Label continuation chunks with their `###` sub-heading, collapse consecutive same-label pages into a range, and draw the header+manifest from a **reserve inside `maxChars`**, since callers treat that number as a hard contract and size their own trailers against it. *(2026-07-20)*

- **ASP.NET Core 8+ carries *two* inbound claim-type maps, and configuring only the legacy one half-works in silence.** `AddJwtBearer` validates with `JsonWebTokenHandler`, which keeps its own `DefaultInboundClaimTypeMap`; `JwtSecurityTokenHandler`'s map no longer reaches the request pipeline. So a helper that rebuilds only the legacy map became a no-op two majors ago — the stock map renamed `role` to the WS-2008 URI while `RoleClaimType` stayed `"role"`, and the symptom was a 403 or a short result set, never an error. Two corollaries: **do not map `name` or `role` inbound at all** — `NameClaimType`/`RoleClaimType` hold the *JWT* spelling, so renaming either makes `Identity.Name`/`IsInRole` resolve against a claim type nothing carries; and a helper reading a claim by its .NET URI (`ClaimTypes.Name`) must fall back to the JWT name, or it answers null for every JWT principal. Assign these process-global statics, never `Clear()`-then-`Add()`: two hosts starting concurrently collide on a half-built map. *(2026-07-27)*
- **A validator resolved from the root provider silently cannot check anything scope-dependent — which is exactly what security checks are.** Entity registration validators ran against the root `IServiceProvider`, so every row-security filter (each needs the caller's identity, a scoped service) threw on resolution and downgraded the whole check to one informational "could not resolve" line. The check that exists to catch an inert row-security filter was disabled by the very thing that makes a filter a security filter. Run startup diagnostics inside `provider.CreateScope()`. Same shape as the concrete-scope hole above: **a diagnostic that skips is indistinguishable from one that passes.** *(2026-07-27)*
- **Authorization applied at `MapControllers().RequireAuthorization()` is invisible to `ActionDescriptor.EndpointMetadata`.** That collection holds attribute-derived metadata only, so a document generator (OpenAPI transformer, analyzer, audit) reading it describes a globally guarded API as fully anonymous. Read `Endpoint.Metadata` instead, matched to the `ApiDescription` via `Endpoint.Metadata.GetMetadata<ActionDescriptor>()?.Id` — an identity match, no route-string comparison. Adjacent trap in the same area: `new OpenApiSecuritySchemeReference(name)` serializes as an empty object unless the host document is passed to it. *(2026-07-27)*
- **Model configuration can be wired from DI — a required call in the consumer's `DbContext` is a design choice, not a constraint.** The archived query filter used to demand `modelBuilder.SetArchivedQueryFilter()` in `OnModelCreating`, on the reasoning that a query filter is model state and only `OnModelCreating` can write it. It is not: an `IDbContextOptionsExtension` whose `ApplyServices` registers an `IConventionSetPlugin` contributing an `IModelFinalizingConvention` writes the same filter from the context's *options*, and model finalization runs after everything `OnModelCreating` configured — so the ordering the named filter needs (`"Regira:Archived"` after the app's own `HasQueryFilter`, anonymous filters re-registered as `"Regira:Model"`) comes for free instead of being the consumer's problem. `IConventionEntityType.SetQueryFilter` applies at convention configuration source and still overrides an explicitly-configured anonymous filter. Prefer this over `ReplaceService<IModelCustomizer, …>`, which forces a choice between `ModelCustomizer` and `RelationalModelCustomizer` and so breaks a provider. **The real limit is not the model — it is DI reach:** options-based wiring covers `AddDbContext`/`AddDbContextFactory` only, so a hand-constructed `new AppDbContext(new DbContextOptionsBuilder<T>()…Options)` (integration tests, design-time factories, seeding tools) builds a model without it, and a DI-resolving startup validator cannot see that model either. Ship the `DbContextOptionsBuilder` extension next to the wiring, and give it a `DbContextOptionsBuilder<TContext>` overload or the chain loses its type before `.Options`. *(2026-08-03)*

- **A policy scheme as the default breaks every document generator that reads the default scheme.** `AddPolicyScheme` forwards rather than authenticating, so it is a *registered* scheme — it passes any "is this scheme registered" filter — that no security-document transformer ever declares. `SecurityRequirementOperationTransformer` fell back to `GetDefaultAuthenticateSchemeAsync()`, so making the selector the default made every guarded operation emit a requirement referencing a `components.securitySchemes` entry that does not exist: a dangling `$ref`, no auth prompt in Scalar/Swagger, and every operation still claiming to need a credential. Fix is an `IAuthenticationSchemeExpander` resolving a forwarding scheme to the schemes behind it, taken as an **optional** constructor parameter so existing registrations keep working — `ActivatorUtilities` fills it when registered and uses the default otherwise, which is verified by a test asserting the policy scheme's name is *absent* from the emitted requirements. Same shape as the two "a diagnostic that skips is indistinguishable from one that passes" entries above: the broken document was still valid JSON. *(2026-07-30)*
- **A scheme-forwarding predicate must test for a *usable* credential, not a present one.** `ForwardDefaultSelector` picks one handler per request, and that handler's `NoResult` ends the request — the other schemes never get a turn. So a rule matching on "the `X-Api-Key` header exists" hands a blank-header request to the API-key handler, which answers `NoResult` for a blank key, and the caller gets a 401 even though the bearer token they also sent would have worked. Every rule tests for non-empty. Corollary for ordering: rules run first-match-wins ascending, so the strongest credential needs the lowest order. *(2026-07-30)*

- **Cross-scheme claim reconciliation has to be additive, and the identity's own name/role types are the load-bearing part.** Folding a provider's claim into a canonical name and dropping the original is the obvious design and the wrong one: Entra emits `roles` (plural), and a consumer reading it directly is entitled to keep working — so `ClaimsNormalizer` *adds* a canonical copy and removes nothing, which bounds the blast radius to "the principal carries more claims than before". What makes the copies actually resolve is passing the canonical spellings as the `nameType`/`roleType` constructor arguments of the `ClaimsIdentity`; `IsInRole` and `Identity.Name` go through the identity's own configured types, so a canonical claim without them is inert. Three consequences worth keeping: de-duplicate role values or a principal carrying two spellings of one role accumulates a copy per spelling; compare claim types case-insensitively, matching `FindFirst`; and keep it **idempotent** — a cookie principal is re-read per request, so anything running per-request (an `IClaimsTransformation`) must clone and short-circuit, which is why normalizing at ticket construction is preferred. *(2026-07-30)*
- **Two claim reads that look right and are not: roles and scopes.** Roles reach a principal under three spellings — plain `role`, Entra's `roles`, and the `ClaimTypes.Role` URI used by the API-key handler and ASP.NET Identity — so a helper reading one answers empty for the schemes using another. Scopes are worse: they arrive as **one space-delimited string** (`"openid profile api.read"`), not one claim each, so `HasClaim("scp", "api.read")` is false against a token that plainly grants it. Entra spells the claim `scp`, most other providers `scope`. Both are covered by `FindRoles()` / `HasScope()`. Also: on an Entra token the stable per-tenant user id is **`oid`**; its `sub` is pairwise per application, so two apps see different values for the same person and keying rows on `sub` silently fragments a user across apps. *(2026-07-30)*

- **A secure-by-default cookie is invisible over plain HTTP, and the failure looks like wrong credentials.** `CookieSecurePolicy.Always` marks the cookie `secure`, and no cookie jar returns a secure cookie over `http://` — so sign-in succeeds, `Set-Cookie` is present in the response, and every subsequent request is anonymous with a `401`. Nothing logs a reason; the natural conclusion is that the sign-in path is broken. Found while writing the cookie tests: six of nine failed until the `WebApplicationFactory` client was given an `https://localhost` base address. `TestServer` performs no TLS but honours the scheme, so testing over `https` reproduces the production shape instead of weakening the policy to suit the test — which is the right trade, because the weakened version would have passed while the shipped default stayed broken for any consumer on plain HTTP. *(2026-07-30)*
- **Cookie auth in an API needs the redirect *events* overridden, not the paths cleared.** Clearing `LoginPath` makes the handler redirect to its own built-in default rather than not redirecting, so the only way to get `401`/`403` is to replace `Events.OnRedirectToLogin` / `OnRedirectToAccessDenied` with status-code writes. Why it matters: the default `302` points at an HTML login page and `fetch`/`HttpClient` follow it transparently, so a script asking for JSON receives `200` and a page of markup — and cross-origin the same thing surfaces as an opaque CORS error rather than "you are not signed in". Also note `CookieAuthenticationDefaults` is already taken by the framework, so the Regira constants are `CookieAuthDefaults`; naming them alike would force every host importing both namespaces to disambiguate. *(2026-07-30)*

- **A multi-tenant Entra API needs an `IssuerValidator`, and the missing check is silent by construction.** With `TenantId` set to `organizations`/`common` there *is* no fixed issuer — every tenant issues under its own id — so a fixed `ValidIssuers` cannot be written and the discovery document advertises a templated `{tenantid}` placeholder. Leave it there and the API accepts tokens from **any** directory: each one is a genuinely valid, correctly signed Microsoft token, just not from a tenant the application ever agreed to trust, so nothing errors and nothing logs. The fix is to compare the issuer against the token's own `tid` claim (accepting both the v2 `{instance}/{tid}/v2.0` and v1 `https://sts.windows.net/{tid}/` spellings). Test it in both directions, per the "prove the filter runs" rule: the *positive* cases are the ones that prove the validator executed, because the templated placeholder issuer would reject them if it had not. Also worth stating in guides: passing issuer validation is not authorization — a multi-tenant app still has to decide whether a given tenant is entitled to anything. *(2026-07-30)*
- **Entra's token shape breaks three reasonable assumptions at once.** App roles arrive as **`roles`** (plural), so `[Authorize(Roles=…)]` answers 403 against a token that visibly contains the role — `RoleClaimType` must be `"roles"`. The audience is issued as **either** `api://{clientId}` **or** `{clientId}` depending on how the client requested the scope, so pinning one form rejects half of otherwise valid callers; accept both. And **`oid`, not `sub`, is the stable user id** — `sub` is pairwise per application, so keying rows on it fragments one person across apps. Adjacent: a registration left at `accessTokenAcceptedVersion: null` issues v1 tokens from `sts.windows.net`, surfacing as `IDX10205`, an error naming neither the version nor the setting; and `groups` carries object GUIDs and is dropped entirely past the token-size limit in favour of `_claim_names`, so a groups-based model fails for exactly the users in the most groups. *(2026-07-30)*
- **`MapInboundClaims = false` is required when normalizing provider claims yourself.** The inbound claim-type map renames claims *before* anything downstream sees them, which pulls the rug out from under a normalizer's source lists — `sub` would arrive as the `ClaimTypes.NameIdentifier` URI and the mapping intended for it never matches. Turning mapping off per scheme keeps provider spellings intact and leaves one place doing the renaming. Related ordering detail when a scheme exposes a `Configure` escape hatch: run the consumer's delegate **first**, then chain your own `OnTokenValidated` onto whatever it left behind — a consumer who replaces `Events` wholesale would otherwise silently drop normalization. *(2026-07-30)*

- **A security control belongs *after* the consumer's escape hatch, not before it.** Both Entra presets expose a `Configure` delegate, and the first cut applied the multi-tenant `IssuerValidator` before invoking it — so a consumer who replaced `TokenValidationParameters` outright silently lost the check and the API went back to accepting tokens from any directory. Chaining the control onto whatever the delegate leaves behind fixes it and has a second benefit: setting it last means it lands on the *new* parameters object if the delegate swapped one in. The general rule for a library with a customization hook: apply defaults before it, invariants after it. Both presets now have a test that replaces `TokenValidationParameters` from `Configure` and asserts the validator survived. *(2026-07-30)*
- **OIDC interactive sign-in is a pair of schemes, and the default wiring is what a hand-rolled setup gets wrong.** The OIDC handler runs the challenge and code exchange; a cookie holds the resulting session. So `DefaultScheme`/`DefaultAuthenticateScheme`/`DefaultSignInScheme` must be the **cookie** and `DefaultChallengeScheme`/`DefaultSignOutScheme` the **OIDC** scheme. Backwards, an `[Authorize]` endpoint either tries to validate an id_token it does not have or redirects to the provider on every single request. Two adjacent traps worth keeping in guides: **sign-out needs both halves** — clearing only the cookie leaves the provider session intact, so the next challenge silently re-signs the user in and "log out" appears to do nothing; and behind a TLS-terminating proxy the handler builds `redirect_uri` from the internal plain-HTTP request, so the callback fails with "Correlation failed" unless `UseForwardedHeaders` runs before the authentication middleware. *(2026-07-30)*

- **The pre-existing `auth/refresh` is a sliding renewal, not a refresh-token flow, and cannot be made into one.** It carries no `[AllowAnonymous]` and reads the caller's id off the bearer principal, so it needs a **still-valid** access token — i.e. it is useless at the one moment renewal matters. A SPA can only use it by polling ahead of expiry, and a tab left closed past the lifespan loses the session. The real flow needs a *separate* anonymous endpoint (`auth/refresh-token`) whose credential **is** the refresh token. Both were kept: the old one is still useful for picking up role changes mid-session. Compatibility shape that made adding it safe on a shipped abstract base: resolve `IRefreshTokenService` from `HttpContext.RequestServices` rather than the constructor (so no consumer's ctor call changes), answer **404 not 500** when it is unregistered, and mark the new DTO fields `[JsonIgnore(WhenWritingNull)]` so an opted-out host's response body stays byte-identical — asserted by a test that checks the property is *absent*, not null. *(2026-07-30)*
- **Refresh-token rotation only buys anything if a replay revokes the whole family.** Rotation alone means a stolen token works once; what makes theft *detectable* is that a rotated token should never be presented twice, so a second presentation proves two parties hold it — and the server cannot tell which one is asking, so the only safe answer is ending the chain. That also kills the attacker's freshly-minted token, not just the victim's. Three details that are easy to get wrong: `RevokeFamily` must reach **already-revoked** tokens (a replayed token is by definition revoked, and the chain is what is being ended); an **absolute** ceiling separate from the per-token lifespan is required or a frequently-rotated chain never expires; and the refresh must take a **claims resolver** rather than replaying the claims captured at sign-in, or a role removed an hour ago stays in force and a disabled account keeps working until the token happens to expire — making it a required parameter is what stops that being skipped. *(2026-07-30)*
- **Hash a refresh token unsalted, and do not carry that reasoning over to passwords.** The store is looked up *by* the hash, so a per-token random salt would make lookup impossible — and it buys nothing here, because a 256-bit random token has no guessable input for a slow KDF to protect. That is the opposite of the password case, where `IHasher`'s per-hash salt and iteration count are the whole point. Related API-shape note: an in-memory default store is the right convenience but must be documented as dev-only in the same breath — it loses every session on restart and is per-process, so behind a load balancer a refresh lands on an instance that has never heard of the token, and **neither failure reproduces on one developer machine**. *(2026-07-30)*

- **A scheme should describe itself once; a document generator should not grow a class per scheme.** The OpenAPI security transformers were one class per scheme, so every new scheme meant another near-identical file carrying its own copy of the `#if NET10_0_OR_GREATER` `IOpenApiSecurityScheme`-vs-`OpenApiSecurityScheme` dictionary split. Replaced by an `ISecuritySchemeDescriptor` each `Add…Authentication` contributes to DI plus one transformer that walks them — which collapses the conditional to a single insertion site and makes adding a scheme a zero-transformer change. Two design points that made it work: the descriptor carries **no OpenAPI type** (it lives in the core package, which does not reference `Microsoft.OpenApi`; the Web package maps it), and the transformer cross-checks each descriptor against `GetAllSchemesAsync()` so a host that configured options but never added the scheme does not advertise it. The superseded per-scheme transformers still work and can be co-registered — everything inserts with `TryAdd`. Note OpenAPI has **no cookie security type**: the convention is an API key with `in: cookie`. *(2026-07-30)*
- **Guides ship inside the packages, so a wrong snippet is a shipped defect.** `Common.Security.csproj` packs `ai/security.examples.md` and `build/Regira.Security.targets` copies it into every consumer's `.regira/instructions/` — so an example carrying an object-keyed `ApiKeys` block (which `ToApiKeyOwner` throws on) or `new Claim(ClaimTypes.Role, …)` (which `RoleClaimType` never resolves) teaches every downstream agent to write code that fails at startup or silently loses roles. Both had been wrong for a while and neither was caught, because nothing compiles the security guides — `tools/GuideVerifier` only covers the Entities family. Two habits that follow: when changing an API, sweep the **examples** files, not just the instructions file; and treat the packed guide list in the csproj as the blast radius. *(2026-07-30)*

- **A policy scheme routing by credential cannot route a *challenge*, because a challenge is the absence of one.** `AddSchemeSelector`'s rules key on what a request carries, so a browser arriving at a guarded page — carrying nothing — fell through to the lowest-ordered rule and got a bearer `401`. In an app whose whole point is interactive sign-in that makes login unreachable, and nothing errors: the selector is working exactly as written. Fix is to route challenges separately (`PolicySchemeOptions.ForwardChallenge`, which the framework checks before `ForwardDefaultSelector`), defaulting to a registered OpenID Connect scheme. **Forbid deliberately stays with the rules** — a forbidden caller *is* authenticated, so their credential identifies the scheme that should render the refusal. General shape worth remembering: authenticate/sign-in/sign-out/forbid are credential-driven, challenge is not, and any "smart" scheme selector has to treat it separately. *(2026-07-30)*
- **Half-wiring a customisation object is worse than not offering it.** The Entra preset exposed a full `ClaimNormalizationOptions` but copied only `RoleClaimTypes` into the bearer options it expanded to — so a caller who customised `SubjectClaimTypes` (directly or via config binding, which *appends* into get-only lists) had it accepted and silently ignored. Two lessons: when a preset expands into another options type, copy field-by-field is the bug — give the options object a `MergeInto` so the copy cannot drift from the shape; and either wire a customisation point fully or do not expose it, because the half-wired version is the only variant that lies. The same latent shape existed in the OIDC cookie `Copy` helper and was fixed with it. *(2026-07-30)*
- **Rotation is only replay-detecting if the revoke is a test-and-set.** `RefreshTokenService` read the record, checked `RevokedAt`, issued the new pair, then wrote the revocation — so two concurrent refreshes of one token both saw `RevokedAt == null`, both succeeded, and the family split into two live chains with nothing detected. The common trigger is not an attacker but a SPA firing two calls after a single `401`. Two things this forced: the store interface needs `Task<bool> TryRevoke(...)` (a conditional write — `WHERE RevokedAt IS NULL` plus a rowcount — not `Update`), and the service must **claim the rotation before issuing anything**, generating the successor token first so the revocation can name it. Getting the interface right mattered more than the race itself: `IRefreshTokenStore` is what consumers implement over their own `DbContext`, and as originally shaped a correct implementation was impossible — `Update` had no way to signal a lost update. An extension point's shape decides whether consumers *can* be correct. *(2026-07-30)*

Two consequences to keep in view: a primer that rewrites a data column in place (trim, round) makes it look like a stamp, and a primer that increments a stamp has to count from `OriginalValue`, the stored one, or an omitted token resets it. Every test token had been a `Guid` or `int` version field, which is how the data-column case went unseen. A rule judged per write also misses the stamp whose new value can equal the old — a content hash, where a stale client writing back what it read reproduces its own token — so an application declares a stamp with `[VersionStamp]`, and only a declaration is something startup validation can rely on: its DTO and initializer checks apply to declared stamps, and are Info for any other token. Changing the runtime's definition of a token without the validator's turned a correct data-column setup into a startup **error**. *(2026-09-16)*
- **A recursion guard held in an instance field is a lifetime counter.** The Word backends stopped a self-including template with `_insertDocumentCounter++` against a limit of 100 and never reset it, so a service kept in a field or a singleton failed for good after 100 nested inserts summed over all its calls — and raced across threads. Bound the depth of the current call instead (`AsyncLocal<int>`, incremented and decremented around the recursive method): it is per flow, cannot wear out, and — because document builds run depth-first — still stops a cycle on its first path however wide each level is. Put the guard on the method every recursion passes through (the document build), not on one of the routes into it, or a template including itself as a header recurses until the stack overflows. Only a test that calls one instance past the limit finds the lifetime bug; a test per fresh instance never does. *(2026-09-16)*
- **`AddHttpClient<TClient, TImplementation>()` names the client after `TClient`, so two packages registering a client for the same interface share one.** Both configure actions then run on it in registration order: `AddGotenbergWord` and `AddOfficeClients` both register `IWordConverter`, and whichever came last set the base address while the other's `Authorization` or licence header stayed on — credentials sent to the wrong server. A package's client needs a name of its own, `AddHttpClient(name, configure).AddTypedClient<TInterface, TImplementation>()` per interface. Which implementation an interface resolves to is still last-registration-wins; only the configuration is separated. *(2026-09-16)*
- **MiniWord matches a tag only when it sits whole in one run and the text between the braces is the key itself.** Its pattern is `{{(\w+(\.\w+)*)}}`, and it does not merge runs, so `{{ title }}`, a dotted collection tag written with spaces, and any tag Word split while it was edited stay literal. Aliasing spaced keys covers only plain keys, because a collection's row lookup splits the tag text itself; rewriting the template before MiniWord reads it covers all of them — per paragraph, over the concatenated text of its `w:t` elements, moving a split tag into the element it starts in. *(2026-09-16)*
- **Switching on first-page or odd/even headers switches the footers too, and the other way round.** Word keeps one flag per section for each, covering both stories, so adding an `Even` header while the footer has only a default version leaves even pages with no footer at all — page numbers vanish from every other page, silently. Setting the flag was the fix for an even header that never rendered, and it regressed the footer; the change that sets such a flag has to give the other story its default content where it has no version of its own. Only a rendered, per-page check catches this: a test that reads the document's text finds every story present. *(2026-09-16)*
- **Aspose.Words' evaluation mode rewrites the headers and footers of every document it *loads*, not only of what it saves.** A header fragment loaded unlicensed arrives with the evaluation banner in its header story, so code that prefers a fragment's header over its body copies the banner instead, and neither the saved file nor the in-memory model shows what a licensed run would do. Anything about headers and footers can only be tested on Aspose with a licence; the other backends' trial output adds text without replacing stories. *(2026-09-16)*
- **`pg_dump --schema` takes a pattern, not a name.** Unquoted, `Sales` is folded to `sales`, and `*`, `?` and `.` are wildcards and separators; a pattern that matches nothing is skipped silently, so the backup exits 0 without the schema. Pass `"Sales"` — the double quotes inside the argument, an embedded quote doubled — and add `--strict-names` so a missing schema fails the dump. Escaping the value for the command line is a second, separate layer on top. Verified against the real tools: `Sales`, `a*b` and `x"y` round-trip, while `sales` and `aXb` stay out. *(2026-09-16)*
- **The MongoDB Database Tools' `--config` file holds the URI as well as the password, and the URI is where the other secrets live.** `tlsCertificateKeyFilePassword` and the `AWS_SESSION_TOKEN` inside `authMechanismProperties` are connection-string options, so keeping every option of a parsed connection string (to connect the way it says) moves them onto the command line unless the URI travels in the file too. A username without a password makes the tools prompt on the console, which a redirected stdin cannot answer: refuse it up front, except for the mechanisms that take no password. *(2026-09-16)*
- **`RESTORE … WITH REPLACE` overwrites a file that belongs to an offline database without a word.** SQL Server's safety check is exactly what `REPLACE` switches off, and an offline database's files are not locked. Before restoring, compare the planned physical names with `sys.master_files` for every other database, and use `REPLACE` only when the target existed — to overwrite the files its own offline drop left behind. *(2026-09-16)*
- **The Office backends take their configuration through the constructor and ship no DI extension.** A licence key is a constructor argument like any other; a container registers the config object and the service under the interfaces the application injects. An extension that registers only the composite `IWordService` fails every consumer who follows the "resolve the narrowest interface" advice, and one that registers them all decides a last-wins contest with every other backend — for nothing a two-line registration cannot do. `Word.Gotenberg` keeps its extension, because a named `HttpClient` needs the factory. *(2026-09-16)*
- **SQL Server's `xp_delete_file` refuses a backup written by a current server as "not a SQL Server backup file"; `sys.xp_delete_files` (SQL Server 2019 and later) deletes it.** Both need `sysadmin`, so server-side cleanup of a `.bak` this process cannot reach is best effort with a logged fallback. Guard on `OBJECT_ID(N'master.sys.xp_delete_files')`, which returns an id for the extended procedure. `xp_delete_file` can also pass over a file without raising anything, so read the outcome back — `INSERT @t EXEC master.sys.xp_fileexist @path` — rather than treat "no error" as "deleted". *(2026-09-16)*
- **`SET SINGLE_USER WITH ROLLBACK IMMEDIATE` from `master`, then `DROP DATABASE`, leaves the one session free for anyone between the two statements; `SET OFFLINE` does not.** The window sits inside one batch and sixteen reconnecting clients did not hit it on LocalDB, so a test guards the offline path under that load without reproducing the race. The price of OFFLINE is that SQL Server keeps an offline database's files when it drops it: a restore `WITH REPLACE` to the same paths overwrites them, and any other file is left on disk. *(2026-09-16)*
- **EF cannot infer an attachment owner's foreign key, and the miss orphans every link row without an error.** `EntityAttachment` carries the owner's key as `ObjectId` and has no navigation back, so an owner collection left to conventions gets a shadow `{Owner}Id`; the pipeline writes `ObjectId`, every link is saved with the shadow key null, the owner's `Attachments` loads empty and `?hasAttachment=true` matches nothing — while the `/{id}/attachments` sub-routes, which filter on `ObjectId`, keep listing the files and mask it. `AttachmentForeignKeyValidator` now reports it at startup from the built model. General shape: **when the pipeline writes one key and the model can map another, validate the model** — the guide step alone was a one-line stub that agents skipped. *(2026-09-21)*
- **The `?archived=` opt-in reaches only the queried `IArchivable` entity, so a filter mirrored onto a dependent is never lifted.** `FilterArchivablesQueryBuilder` is scoped to `IArchivable` and suspends only the named archived filter; a mirrored `HasQueryFilter(x => !x.Parent!.IsArchived)` is the app's own filter on a non-archivable type. An archived parent's children therefore disappear from the API for everyone, the administrator who archived it included. The guides offer the alternative (keep the parent out of the children's reads); the validator still warns on that shape because it reads the model, not the queries. *(2026-09-21)*

- **`SavedChanges` is not the commit, and EF's own transaction does not raise its events where you would expect.** Post-commit work cannot key off one hook. A single-statement save opens no transaction at all; a multi-statement save opens one and raises `TransactionCommitted` *before* `SavedChanges`, with `Database.CurrentTransaction` still set inside that event; inside an explicit `BeginTransaction()`, `SavedChanges` runs with `CurrentTransaction` set and the commit comes later. So the rule is: at `SavedChanges`, no current transaction means committed; otherwise hold the work for that transaction's `TransactionCommitted` — keyed on the `DbTransaction` itself, not on EF's `TransactionId`: contexts sharing one transaction through `UseTransaction` each give it an id of their own, and only the context that commits raises the event. A transaction disposed without `Commit()` or `Rollback()` raises neither event; held in a `ConditionalWeakTable` keyed on the `DbTransaction`, what waits on it is collected with it — *unless the provider reuses the object*. Npgsql hands the same `NpgsqlTransaction` to every `BeginTransaction` on a pooled physical connection, so what an abandoned transaction left behind rode along with the next request's commit (SQLite and SqlClient create a new object per begin, so only a PostgreSQL test shows it). Drop what waits on an object at `TransactionStarted` on it. Do not drop it at `TransactionUsed`, which every context sharing a live transaction raises. The savepoint events carry no savepoint name, so a rollback to a savepoint cannot be followed. An ambient `TransactionScope` is invisible to EF's transaction events (`CurrentTransaction` is `null`); wait on `Transaction.Current.TransactionCompleted` instead. SQLite cannot enlist, and EF throws `AmbientTransactionWarning` by default, so that path is testable there only with the warning ignored. *(2026-09-23, keyed on the `DbTransaction` 2026-09-24)*
- **An entry's `OriginalValues` are what its writer attached, not what the database holds — and its flags cannot tell you which.** `Update(detachedEntity)` flags every property modified with the original equal to the new value; a stub `Remove(new T { Id = id })` has empty originals, and the archivable primer turns that stub delete into an update that keeps them; a stub `Attach(new T { Id = id })` that is then edited flags only what was edited — the shape a tracking query leaves — over the stub's empty originals. So only positive evidence counts. `ChangeTracker.Tracked` reports `FromQuery` for what a tracking query loads. Subscribe before the first row is materialized — a command interceptor's `ReaderExecuting` is early enough — and again on every pool lease: a pooled context drops its `ChangeTracker` event handlers when it is returned, and `ContextId.Lease` moves. The write path marks what it loads itself (`TrackAsUpdateOf`'s `OriginalValues.SetValues(stored)`). Key such a mark on EF's internal entry (`entry.GetInfrastructure()`), not on the entity: `ChangeTracker.Clear()` detaches everything without raising `StateChanged`, so an entity-keyed mark survives it and vouches for the same instance attached again with its own values. `Attach`, `Update` or `Remove` after a detach creates a new internal entry, and setting the state of an `EntityEntry` held across the detach tracks the old one again with the originals it had, so the mark stays true either way. `GetDatabaseValues()` reads the stored row and ignores query filters, so it also finds an archived row. For many rows, one no-tracking query with `IgnoreQueryFilters()` does the same: key `IN` a list, projecting `EF.Property` of every flattened property, with complex members through nested `EF.Property` calls, which EF 8 and 10 both translate. It fills a `Clone()` of the entry's originals property by property, because the `PropertyValues` indexer takes complex members. Put what it returns in a snapshot of your own: overwriting `OriginalValues` changes the concurrency `WHERE` clause and the token decision (the 2026-09-16 entry). *(2026-09-23, positive evidence and batching 2026-09-24)*
- **Work deferred to an ambient transaction's completion can outlive the DI scope that queued it, and whatever it throws escapes from `TransactionScope.Dispose()`.** `TransactionCompleted` fires inside the caller's `Dispose`, which may come after the request scope that saved has been disposed: resolve what the deferred work needs (the scope factory, the logger) when it is queued, not when it runs, and catch everything in the handler, or the caller's `using` throws an exception that has nothing to do with its own code. Run the work under `TransactionScopeOption.Suppress`, so a write it makes does not try to enlist in the transaction that just ended. *(2026-09-23)*

- **Turning a delete into an update writes every column unless you unflag them — and unflagging reverts, not just skips.** `entry.State = EntityState.Modified` flags every property, so an update made from a `Deleted` entry sends the entity's values for the whole row, and a deleted entry is often a stub (`Remove(new T { Id = id })`) whose values are all empty: the archivable primer wrote them over the stored row. Unflag with `PropertyEntry.IsModified = false` — which also **resets the current value to the original**, so any value you mean to write must be set *after* the reset, or it silently reverts (the first attempt archived nothing that way). Values a later primer changes are still written: DetectChanges runs after the `SavingChanges` interceptors and flags whatever differs from the original. Two more consequences of the stub's empty originals: a primer that treats an empty original as "never set" and mints a value (`Created`) rewrites a stored one, so an update that does not write a column must leave it alone; and an empty concurrency token in the `WHERE` matches nothing, the same stub problem the hard-delete path had already solved. Nor can the update the primer makes be told from one that archives by its flags: a stub attached with `IsArchived = true` flags the same single column, so the primer records the entries it converts, and the token primer reads that record. *(2026-09-23)*
- **By the time a `SavingChanges` interceptor sees a delete, EF has already cascaded it to the loaded dependents — and left no trace of doing so.** With the default `CascadeDeleteTiming.Immediate`, `Remove(parent)` deletes every loaded dependent of a cascading relationship, detaches an added one, and nulls the foreign key of an optional one. A loaded dependent on a required relationship that does not cascade (`Restrict`) makes it throw instead. `Remove` of an untracked instance attaches the graph it carries first, so a parent read without tracking but with its children included cascades the same way. A primer that turns the delete into an update (the soft delete) has to undo that. A deleted dependent can be set back to `Unchanged`: its pending edits survive, and DetectChanges flags them again. An added one EF detached is still in the parent's navigation. `PropertyEntry.IsModified = false` resets a nulled key to the original. The cascade is indistinguishable from a caller's own `Remove(child)`, so the undo takes those back too. `ChangeTracker.StateChanged` fires for the parent *before* the cascade, but changing its state in that handler stops the cascade only on EF 10; EF 8 cascades on the state it was given. Where the code does the removing, avoid the cascade instead: set `CascadeDeleteTiming = OnSaveChanges` around the `Remove` and put it back after. EF then cascades during the save, after the `SavingChanges` interceptors, and for a soft delete there is nothing left to cascade. A context that runs with a deferred timing of its own has cascaded nothing before the primers, so there is nothing to undo. Per-pass state such as "cascades undone" must be reset when a pass *starts*: a primer that throws skips whatever the pass does at its end, and the next pass on that context would inherit the stale flag. What a retry of the same save still needs (the record of which updates are soft deletes) is cleared only when a pass completes. *(2026-09-24)*
